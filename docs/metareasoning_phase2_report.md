# Phase 2: Metareasoning — Final Report

**Дата:** 2026-11-06  
**Статус:** COMPLETED (с оговорками)  
**Достигнутое улучшение:** 7.6% (цель ТЗ: ≥20%)

## Резюме

Этап 2 исследовал возможность снижения стоимости сертификации через адаптивную политику выбора кандидатов для верификации. Достигнуто улучшение **7.6%** (с 1.5793 сек до 1.4586 сек на сертификат), что ниже целевого порога 20%, установленного в ТЗ v2.1.

## Архитектурное ограничение

Анализ структуры затрат показывает фундаментальное ограничение:

| Компонент | Время | Доля бюджета |
|-----------|-------|--------------|
| Оптимизация L-BFGS-B (500 итераций) | ~0.84 сек | 98.5% |
| Верификация C++ (Krawczyk) | ~0.013 сек | 1.5% |

**Математический предел экономии:** Даже полный отказ от верификации для 50% кандидатов (что невозможно без потери сертификаций) дал бы улучшение всего **0.4%**, а не 20%.

## Испробованные подходы

### 1. Трёхуровневая политика (grad_norm пороги)
- **Идея:** Пропускать верификацию для кандидатов с `grad_norm > 1e-2`, дооптимизировать пограничные (`1e-3 ... 1e-2`), сразу верифицировать хорошие (`< 1e-3`).
- **Результат:** 7.6% улучшения.
- **Проблема:** Дооптимизация (refine) стоит **дороже** верификации (0.05 сек vs 0.013 сек), поэтому добавление refine УВЕЛИЧИВАЕТ общую стоимость, даже если пропускаем часть верификаций.

### 2. Fast-fail на уровне оптимизации (50 итераций)
- **Идея:** Запустить 50 итераций L-BFGS-B, если энергия > -35 или grad_norm > 1e-2 — пропустить полностью (экономия ~0.75 сек).
- **Результат:** 0 сертификаций (100% пропусков).
- **Причина:** За 50 итераций L-BFGS-B не успевает показать, хороший кандидат или плохой. Все кандидаты имеют `grad_norm > 1e-3` после 50 итераций, невозможно установить дискриминативный порог.

### 3. Physics-informed пороги (hessian condition number)
- **Идея:** Пропускать верификацию, если число обусловленности гессиана > 1e7 или минимальное собственное значение < 1e-4.
- **Результат:** 0% улучшений (пороги не отсеивают ни одного кандидата, все имеют condition number < 2e6).
- **Причина:** Распределения признаков для успешных и неуспешных верификаций почти полностью перекрываются.

### 4. ML-предиктор (ChatGPT анализ)
- **Идея:** Обучить модель (Random Forest, XGBoost) на признаках (energy, grad_norm, hessian condition, min_pairwise_dist) предсказывать успех верификации.
- **Результат:** AUC ~0.6 (близко к случайному угадыванию).
- **Причина:** Признаки в конце оптимизации не несут информации о том, пройдет ли интервальный метод Кравчика проверку. Верификатор падает из-за interval overestimation или вырождения гессиана, что не коррелирует с float-признаками.

## Best Result (зафиксирован)

**Политика:** Metareasoning (Adaptive) с порогами:
- `grad_norm < 2.5e-03`: немедленная верификация
- `2.5e-03 <= grad_norm < 1.0e-02`: дооптимизация (gtol=1e-8, maxiter=2000) + верификация
- `grad_norm >= 1.0e-02`: пропуск

**Метрики:**
- Baseline: 53/100 сертификаций, 1.5793 сек/сертификат
- Metareasoning: 58/100 сертификаций, 1.4586 сек/сертификат
- **Улучшение: 7.6%**

**Побочный эффект:** Metareasoning увеличил число сертификаций с 53 до 58 (дооптимизация спасла 5 кандидатов), но ценой небольшого увеличения среднего времени.

## Рекомендации для будущих итераций

1. **Сменить метрику:** Вместо `cost_per_cert` использовать `success_rate_per_hour` (число сертификаций в час). Тогда удешевление оптимизации (даже ценой снижения success rate) может дать выигрыш.

2. **Удешевить оптимизацию:** Заменить L-BFGS-B на более быстрый метод (например, CG с аналитическим градиентом) или использовать Numba JIT для ускорения вычисления энергии/градиента.

3. **Улучшить генератор:** Вместо случайных стартов использовать Basin Hopping или генерацию из известных минимумов (perturb known). Это увеличит success rate без изменения мета-политики.

4. **Признать ограничение:** Если 20% недостижимы в текущей архитектуре, зафиксировать это как научный результат и перейти к следующему этапу.
